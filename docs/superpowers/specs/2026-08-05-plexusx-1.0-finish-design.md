# PlexusX 1.0 — the finish

Written 2026-08-05.

Brief: the app still reads as amateur despite the features being there. Four days to a version
that can be sold to a large audience. Add advanced colour deep enough that a shared code is
worth asking for.

Scope is the app itself. Certificates, storefront and legal pages are tracked in
`docs/ROADMAP.md` and are deliberately out of scope here.

## What the audit actually found

The code is not the problem. 841 tests pass, disposal is careful, settings migrate, the
comments explain intent. The problem is the shell around it — and it is concentrated in the
first ten seconds of use.

Ranked by how much each one contributes to the "student made this" reading:

1. **Blurry on scaled displays.** `Program.cs` sets `HighDpiMode.SystemAware`, so Windows
   bitmap-stretches the whole window at 125% and 150% — most gaming laptops, most 1440p and
   4K monitors. Every competitor is sharp. This is the single biggest signal.
2. **The window cannot be resized.** Borderless, `MinimumSize` set, every control carries
   Anchor flags for a resize that can never happen: there is no `WM_NCHITTEST` handler in the
   codebase. The plumbing exists and is unreachable. No maximize either.
3. **Eleven raw `MessageBox.Show` calls** in a glass-themed app, including on the common paths
   (update prompts, game-page confirmations).
4. **Window position and size are never remembered.** The popup's position is remembered; the
   main window's is not.
5. **No type scale.** 98 `new Font()` calls across 12 sizes.
6. **No spacing scale.** Every page invents its own margins, then nudges with one-off offsets.
7. **Fonts allocated inside paint loops** — `NavButton`, `GameCard`, `KeybindsPage`.
8. **Focus states on 3 controls out of ~20.** Tabbing through the app is invisible.
9. **No keyboard navigation** in the shell; no Escape to close; no `KeyPreview`.
10. **Two tooltips in the entire app.** No control explains what it does.
11. **Zero `AccessibleName`.** Owner-drawn controls are invisible to screen readers.
12. **Title bar close/minimize are `Label`s** with text glyphs, no hover states.
13. **30fps fixed-interval animation** for an audience that bought high-refresh monitors.
14. **85% window transparency by default** — wallpaper bleeds through every label on first run.
15. **99 hardcoded colours**, ~40 of them outside `ThemeCatalog` and immune to theme changes.

## The pipeline constraint that shapes advanced colour

Two live paths, with very different capabilities. This was not previously written down and it
determines what can honestly be built.

**The colour matrix** — `ColorAdjust.Build()`, applied via the Magnification API today (or the
DX11 shader when enabled). A linear 5×5 matrix. It can express saturation, vibrance,
brightness, contrast and white balance. It cannot express anything non-linear, by definition.

**The gamma ramp** — `DisplayGammaRamp`, a 3×256 per-channel 16-bit lookup table applied by the
GPU on scanout. Non-linear, works on every GPU, already wired with a test seam, already resets
on shutdown, already reports driver refusal. **It currently carries one power curve copied
identically to all three channels.**

That second path is a complete colour-grading engine running at a fraction of its capability.
Advanced colour comes from there. No new rendering, no DX11 dependency, no anti-cheat surface.

### What each path can and cannot deliver

| Control | Path | Deliverable |
|---|---|---|
| Saturation, Vibrance, Brightness, Contrast | matrix | exists |
| Temperature | matrix | exists |
| Tint (green↔magenta) | matrix | new, trivial |
| Highlights, Shadows, Whites, Blacks, Fade | gamma ramp | new |
| Shadow/Midtone/Highlight tint | gamma ramp, per channel | new |
| HSL per colour range | DX11 shader only | **not deliverable** |
| Sharpen | needs neighbouring pixels | **not deliverable** |
| Vignette | needs pixel position | **not deliverable** |

HSL, Sharpen and Vignette are excluded rather than stubbed. The reason is product, not
engineering: the growth loop is people sharing codes. A code that does not reproduce the look
on the recipient's machine destroys trust in the mechanism that spreads the app. Every control
must survive being shared.

## Design

### 1. Design tokens

A single source for typography and spacing, replacing 98 ad-hoc `new Font()` calls and the
per-page magic numbers.

Type roles — Display, Title, Heading, Body, Label, Caption, Micro. Seven, not twelve. Fonts are
cached and owned centrally, so nothing allocates one inside a paint handler.

Spacing scale — a geometric step (4, 8, 12, 16, 24, 32, 48) that every page uses. No page
defines its own margin constant again.

Both scale by DPI, which is what makes the next item possible.

### 2. Per-monitor DPI

`HighDpiMode.PerMonitorV2`, with layout driven through the token scale rather than hardcoded
pixels. Pages are converted one at a time, each verified at 100%, 125%, 150% and 200%, and on
a monitor-to-monitor drag between different scale factors.

This is the largest single item and it touches every page. It is scheduled first because
everything else is easier once layout is DPI-relative, and harder if retrofitted after.

### 3. Window chrome

- `WM_NCHITTEST` for edge and corner resizing, honouring the existing `MinimumSize`. The Anchor
  flags already present across every page start doing their job for the first time.
- Maximize button, double-click-title to maximize, and Aero Snap.
- Window position and size persisted to `AppSettings`, validated against the live monitor
  layout on load so a saved position on an unplugged monitor cannot strand the window
  off-screen. The popup's existing validation is the model to follow.
- Title bar buttons become owner-drawn controls with proper hit targets and hover states —
  red on close, matching platform convention.

### 4. One glass dialog

A single themed dialog (title, body, primary/secondary action, optional icon) replacing all
eleven `MessageBox.Show` call sites.

One exception, kept deliberately: `Program.cs`'s fatal-error handler stays a native
`MessageBox`. It must render when the themed UI is the thing that failed.

### 5. Advanced colour

Fifteen controls in four groups, on the Display page behind a "Advanced" disclosure so the
default view stays as simple as it is today.

- **Basic** — Saturation, Vibrance, Brightness, Contrast, Gamma *(existing)*
- **Tone** — Highlights, Shadows, Whites, Blacks, Fade *(gamma ramp)*
- **Colour** — Temperature *(existing)*, Tint *(matrix)*
- **Colour Balance** — Shadow tint, Midtone tint, Highlight tint *(per-channel gamma ramp)*

A new `ToneCurve` type builds the 3×256 ramp from the tone and balance values. Pure maths,
no display required, unit-tested exactly like `ColorAdjust` and `GammaCurve` already are.
`GammaCurve.Build` becomes one case of it, and its existing behaviour is pinned by the tests
that already cover it.

Each group gets a reset. Neutral for every new control is the value that produces an identity
ramp, so an untouched advanced section is provably a no-op — which the identity check can then
use to skip the ramp entirely.

### 6. Share codes

The format already versions by body length: 9 characters is pre-contrast, 13 is current. A
third length carries the advanced values.

Encoding stays adaptive. When every advanced control sits at neutral, the encoder emits the
existing 13-character code. Only a genuinely graded look produces the longer one. Casual codes
stay short enough to read off a stream; detailed looks still travel exactly.

Every code previously posted anywhere keeps decoding. That is a hard requirement and it gets a
regression test per format generation.

The feature moves from the bottom of Settings onto Display, where the sliders it describes
already live.

### 7. Interaction and feel

- Focus rings on every interactive control. `PresetChip` is the existing pattern to copy.
- Keyboard navigation through the nav rows, Escape to close, Accept/Cancel on every dialog.
- Tooltips on every control whose name does not fully explain it.
- `AccessibleName` and `AccessibleRole` on owner-drawn controls.
- Animation driven at the display's actual refresh rate rather than a fixed 33ms tick.
- Default opacity to 100%. The slider stays; users who set their own value keep it.

## Out of scope

**Referral / "share PlexusX, get a key".** Needs key generation, referral attribution and abuse
prevention — a server, not an app feature. Shipping it half-built invites farming. It follows
this release.

**HSL, Sharpen, Vignette.** Not possible on the live rendering path (§ pipeline constraint).
These become the headline of the release that proves out DX11.

**Folding the Profile Editor into Display.** Identified in the road-to-1.0 doc as the highest
value cleanup remaining, and it still is — but it changes what auto-apply does to people's
screens, and this release is already changing the colour pipeline. Two risky changes to the
same subsystem in one release is how a regression gets missed.

## Testing

The colour maths is pure and gets tested first — `ToneCurve` builds correct ramps, neutral
inputs produce an identity ramp, every control's extremes stay in range.

Code round-tripping is property-tested as the existing code already is: encode then decode
returns the original for any valid combination, every historical format still decodes, and a
single-character typo is always rejected.

DPI is verified by hand per page at four scale factors plus a cross-monitor drag, because it
is a rendering property no unit test observes.

The existing 841 tests must stay green throughout. Any that need changing indicate a behaviour
change that needs to be deliberate.

## Order

1. Tokens + DPI — everything else is cheaper afterwards
2. Window chrome + glass dialog
3. Advanced colour + code format
4. Focus, keyboard, tooltips, accessibility, motion, share-code placement

Sequenced so that if day 4 is lost, what ships is still a sharp, resizable, properly-dialogued
app with advanced colour — a sellable product. The items most likely to slip are the ones a
buyer is least likely to notice in the first session.
