# PlexusX 1.0 — "We own the monitor" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Do NOT dispatch subagents — this codebase carries heavy accumulated context and a fresh agent re-derives it at the user's expense.

**Goal:** Reshape PlexusX around one job — *everything you look at* — then finish it. Cut the two tabs that were about what the PC is doing, build the three that are about what the monitor shows, clear the legal blockers, and lock the visual rules down with tests.

**Design spec:** `docs/superpowers/specs/2026-08-07-plexusx-monitor-philosophy-design.md`

**Architecture:** Display (software colour) → Resolution (display mode) → Monitor (physical panel via DDC/CI) is a three-layer stack over the same picture. Crosshair, Settings and Account support it. Everything else is deleted.

**Tech Stack:** C#/.NET 8, WinForms, xUnit, GDI+ owner-drawn controls, `dxva2.dll` for DDC/CI, Inno Setup.

**Out of scope (part 2/2):** website, backend, payment webhooks, merchant-of-record, code-signing purchase.

## Global Constraints

Every task implicitly includes this section. Phase 0 turns each rule into a test; after Phase 0 a violation is a build failure, not an opinion.

### UI contract

- **U1 — No stock Win32 controls outside `Controls/`.** `Button`, `TextBox`, `ComboBox`, `CheckBox`, `RadioButton`, `LinkLabel`, `NumericUpDown`, `TrackBar`, `GroupBox`, `ListBox`, `TabControl`. Use `GlassButton`, `GlassTextBox`, `GlassDropdown`, `ToggleSwitch`, `ChipButton`, `FlatSlider`, `GlassLink`. `Label` and `Panel` are fine. `GlassTextBox` hosting a real `TextBox` is the single permitted exception and lives in one file.
- **U2 — No hardcoded colours.** Everything from `Theme.*`. `Color.FromArgb` only for alpha-blending a `Theme` colour, or inside `Controls/`, `Theming/`. No `SystemColors.*` anywhere.
- **U3 — Fonts from `Design/Fonts`.** No `new Font(Theme.FontFamily, …)` outside `Design/`. Explicit `"Consolas"` for codes/hex is the exception.
- **U4 — Spacing from `Design/Tokens`.**
- **U5 — Nothing clipped or overlapping.** Measure wrapped text with `TextRenderer.MeasureText(…, WordBreak).Height + 6` — `MeasureText` and `Label` do not lay out identically, and that gap slices descenders off the last line.
- **U6 — Every page reaches its own content.** `AutoScroll` + `FitScrollToContent()`. Wheel works with the cursor over any descendant.
- **U7 — Keyboard-reachable and announced.** `TabStop`, `AccessibleRole`, `AccessibleName` tracking `Text`, visible focus ring. Arrow-key handlers must claim them in `IsInputKey` or WinForms eats them as dialog navigation.
- **U8 — Paints in every state:** normal, hover, pressed, focused, **disabled**, at 1×1 and 2000×40, in all four themes, without throwing. Disabled must look disabled.
- **U9 — User-visible numbers use `CultureInfo.InvariantCulture`.** A Czech Windows must not render `1,00`.
- **U10 — No dead affordance.** Unset says "Not set", never `(none)` or `0x0`.
- **U11 — Dialogs are `GlassDialog` or handle Enter/Escape by hand.** `GlassButton` is not `IButtonControl`; `AcceptButton`/`CancelButton` silently do nothing.
- **U12 — No mojibake** (`â€`, `Ã`, `Â`).

### System contract

- **S1 — Nothing under the hood.** No registry tweaks, no game config writes, no process handles, no priority changes. This plan *removes* the last of these.
- **S2 — No raw exception dialogs.** The native `MessageBox` in `Program.cs` is deliberate and stays — the themed dialog needs a working WinForms context, which is exactly what may be broken.
- **S3 — Settings never silently lost.** Every new persisted field gets a `SettingsStore` round-trip test.
- **S4 — Never block the UI thread.** DDC/CI calls are slow (tens of ms per read, sometimes hundreds). They go off-thread.
- **S5 — Honest claims only.** Where a capability depends on the hardware, the probe decides the wording. Never claim monitor control on a monitor that refused it.
- **S6 — Never leave the panel wrong.** Read and store the original value before the first DDC/CI write. Always offer revert.

### Process contract

- **P1 — TDD.** Failing test, minimal implementation, green.
- **P2 — Full suite green before every commit.** Baseline **1204 passing, 4 skipped**. Deletions will lower the count legitimately; record the new number each time.

- **P5 — Evidence before claims.** Paste the test line. Say what was skipped.

Log to `docs/OVERNIGHT-LOG.md`. Do not block.

- **Cutting Audio Edge** — works on merit, fails the philosophy. Leave it.

```csharp
using System;
using System.Collections.Generic;
using System.IO;
using System.Linq;
using System.Text.RegularExpressions;
using Xunit;

namespace VibranceHud.Tests
{
    /// <summary>
    /// The design rules, as tests.
    ///
    /// Written because "this doesn't match the theme" kept arriving as a message instead of a
    /// build failure. A stock Win32 control cannot be themed - a flat Button keeps square
    /// corners and the system focus rectangle - so the only rule that holds is that it must
    /// not be constructed at all outside the one place that wraps it.
    /// </summary>
    public sealed class UiContractTests
    {
        internal static string RepoRoot()
        {
            var dir = new DirectoryInfo(AppContext.BaseDirectory);
            while (dir != null && !File.Exists(Path.Combine(dir.FullName, "VibranceHud.csproj")))
                dir = dir.Parent;
            Assert.True(dir != null, "could not find the repo root from " + AppContext.BaseDirectory);
            return dir!.FullName;
        }

        internal static IEnumerable<(string Path, string Text)> ShippingSources()
        {
            string root = RepoRoot();
            foreach (var file in Directory.EnumerateFiles(root, "*.cs", SearchOption.AllDirectories))
            {
                string rel = Path.GetRelativePath(root, file).Replace('\\', '/');
                if (rel.StartsWith("tests/") || rel.StartsWith("docs/")
                    || rel.Contains("/bin/") || rel.Contains("/obj/")
                    || rel.StartsWith("bin/") || rel.StartsWith("obj/"))
                    continue;
                yield return (rel, File.ReadAllText(file));
            }
        }

        private static readonly string[] Banned =
        {
            "Button", "TextBox", "ComboBox", "CheckBox", "RadioButton",
            "LinkLabel", "NumericUpDown", "TrackBar", "GroupBox", "ListBox", "TabControl",
        };

        private static bool IsWrapper(string rel) =>
            rel.StartsWith("Controls/") || rel == "NavButton.cs" || rel == "SwatchButton.cs";

        [Fact]
        public void NoStockWin32ControlIsConstructedOutsideTheWrappers()
        {
            var offences = new List<string>();

            foreach (var (rel, text) in ShippingSources())
            {
                if (IsWrapper(rel)) continue;

                foreach (var control in Banned)
                {
                    // "new Button {" / "new Button(" - not "new GlassButton", not "new ButtonX".
                    var rx = new Regex(@"(?<![\w.])new\s+" + control + @"\s*[({]");
                    foreach (Match m in rx.Matches(text))
                    {
                        int line = text.Take(m.Index).Count(c => c == '\n') + 1;
                        offences.Add($"{rel}:{line} constructs a stock {control}");
                    }
                }
            }

            Assert.True(offences.Count == 0,
                "Stock Win32 controls cannot be themed - use the Glass* equivalent:\n  "
                + string.Join("\n  ", offences));
        }
    }
}
```

### Task 1.1: Probe the physical monitor

**Files:** Create `Monitors/PhysicalMonitor.cs`, `Monitors/MonitorProbe.cs`; Test: `tests/VibranceHud.Tests/MonitorProbeTests.cs`

**Interfaces:**
- Produces: `MonitorProbe.Probe()` → `IReadOnlyList<MonitorCapability>` where
  `MonitorCapability(string Description, bool SupportsBrightness, bool SupportsContrast, bool SupportsRgbGain, int BrightnessMin, int BrightnessCurrent, int BrightnessMax, string Refusal)`.
  `Refusal` is `""` when the panel answered, otherwise a plain-English reason.
- Produces: `PhysicalMonitor` — an `IDisposable` handle wrapper exposing `TryGetBrightness`, `TrySetBrightness`, `TryGetContrast`, `TrySetContrast`, `TryGetRgbGain`, `TrySetRgbGain`.

# PHASE 5 — Display: advanced colour, presets, previews, A/B

*The core of the product. Everything here is software colour, already proven.*

**Order matters: the channels come before the presets that use them.** Six sliders (saturation, vibrance, brightness, gamma, contrast, temperature) cannot express the difference between "Rust brown-grey" and "CS2 concrete-orange" — every preset would land in roughly the same place. The advanced channels are what make a preset worth picking.

### Task 5.0a: Advanced colour engine — lift / gamma / gain, and tint

**Files:** Modify `ToneSettings.cs`, `ToneCurve.cs`; Test: `tests/VibranceHud.Tests/ToneCurveTests.cs`

**What is actually possible, and what is not.** The display gamma ramp is a 3×256 per-channel lookup table — one independent curve for red, green and blue. That is genuinely powerful and it is what the app already grades on. It **can** do:

- **Lift / Gamma / Gain** — the standard three-way corrector (shadows / midtones / highlights), independently per channel. This is the CapCut/DaVinci model.
- **Tint** (green ↔ magenta), which completes the white-balance pair with the existing Temperature (blue ↔ orange).

It **cannot** do hue-selective work — "make only the greens duller" needs a full colour transform, not a per-channel curve. The linear colour matrix can approximate some of it, but the DX11 path is disabled. **Do not promise HSL. Do not add a hue wheel.** (S5.)

**Interfaces:** `ToneSettings` gains `int ShadowLift`, `int Midtones`, `int Highlights`, `int Tint` — all percent-style ints centred on a neutral, matching the existing field style. Every one needs a `Resolved*` accessor treating `0` as untouched, for the same reason `ResolvedGamma` exists: a record-struct parameterless constructor bypasses primary-constructor defaults, and that shipped once as a black screen.

- [ ] **Step 1: Failing tests**
  - Neutral settings produce an identity ramp (no visible change).
  - Raising `ShadowLift` raises low-end output and leaves the top end alone.
  - Raising `Highlights` raises the top end and leaves the bottom alone.
  - `Midtones` moves the middle and pins both ends.
  - `Tint` moves green against red+blue; `Temperature` moves blue against red. Applying both is order-independent.
  - Every combination stays inside `0..65535` — a ramp that overflows is a corrupt screen.
  - **A default-constructed `ToneSettings` is neutral**, guarding the `Neutral => new()` bug directly.
- [ ] **Step 2: Run. Expect FAIL.**
- [ ] **Step 3: Implement in `ToneCurve`.** Compose in a fixed order — lift, then gamma/midtones, then gain, then white balance — and document that order in the file, because changing it silently changes every saved preset.
- [ ] **Step 4: Run. Expect PASS.**
- [ ] **Step 5: `SettingsStore` round-trip test for the four new fields (S3).** Remember `[JsonIgnore]` on any `Normalized`-style self-returning property — that recursion once broke *every* settings save.

## Execution order and pacing

1. **Phase 0** — rules. Everything depends on it.
2. **Phase 1** — DDC/CI spike. Early, because it decides Phase 6's shape.
3. **Phase 2** — the cuts. Mechanical, huge clarity gain, do before building new things.
4. **Phase 3** — theme completion.
5. **Phase 4** — legal. Independent; start it if anything else stalls.
6. **Phase 5** — Display presets. The core product.
7. **Phase 6** — Monitor tab (gated on 1.1).
8. **Phase 7** — crosshair codes.
9. **Phase 8** — release readiness. Last.

**If time runs short, cut from Phase 7 upward.** Never cut Phase 0 (stops the problem recurring), Phase 2 (the app must match the philosophy) or Phase 4 (legal blockers).

**Efficiency rules for an unattended run:**
- Re-read a file only when the last edit was not yours.
- Filtered tests during a task; full suite only before a commit.
- Render in one batch per phase, not per task.
- Prefer editing a shared helper over N call sites — the `FlatButton` change fixed 40 buttons in one edit.
- No subagents.
